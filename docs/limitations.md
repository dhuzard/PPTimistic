# Current implementation scope

Working: multi-project setup, English/French first-run prompts, three themes, nine layouts, native editable text/diagrams/arrows/charts, explicit CSV-bound chart selections, local source extraction and hashes, optional claim-to-source links and local review reports, notes, captions, image prompts and local attachment, manual multilingual import/export with source-freshness checks, consistency checks, feedback logs, structured revisions, protection baselines, output hashes/history, artifact freshness checks, local delivery bundles, actual PPTX validation, optional local rendering, stable-ID revision previews, slide PNGs, PDF and contact sheets. Automated tests generate real bilingual decks and use no paid integrations.

Deliberate limits:

- No external image or AI translation adapter ships enabled. Interfaces, prompts and manual/local workflows are implemented; automatic image generation and automatic scientific translation are extension work.
- Document extraction is not automatic research synthesis. Except for literal Markdown plan import, an agent or person must author the content. Reference-image style analysis also requires an agent/person who actually inspects the images.
- Claim-to-source links are optional, authored records. A literal excerpt match checks traceability to local extracted text; it does not prove that the excerpt supports the claim, nor does it infer claims from slide text. The local claim report withholds excerpt text by default, but can still contain confidential slide wording and source paths.
- Advanced command help, errors and diagnostic details are mainly English. The first-run wizard and starter content support French and English. Other canonical BCP 47 output locales can be authored manually; the starter source content supports en-US and fr-FR.
- Text layout checks use conservative glyph-aware estimates, not PowerPoint font metrics. They can reject text that might fit or miss a font-specific issue. Long chart labels receive a review warning, but internal chart collisions still require full-size visual inspection. Object overlap checks cover logical content boxes; deliberate shape backgrounds/connectors are not independently collision-tested. Citations are printed verbatim; their bibliographic truth is not automatically verified.
- Charts currently use native vertical bars. CSV bindings copy finite numeric cells from explicit columns/rows, with at most 15 significant decimal digits; they do not compute transformations. Table layout, other chart types, bibliography resolution, data transformations, OCR, automatic PPTX import/reconciliation, DOCX embedded image extraction and arbitrary user positioning are not included.
- Translation checks protect common numeric/unit/DOI notation and exact glossary terms. Fingerprints detect source changes after a recorded translation review; older translations without a fingerprint are flagged as untracked. These checks cannot establish semantic/scientific equivalence, parse all Unicode scientific notation, identify unchanged prose as necessarily mistranslated, or provide full RTL/CJK typography handling.
- Fictional charts receive a mandatory visible disclosure. English and French wording is built in; other locales require a manually supplied `fictionalNotice` in localized content, with scientific review of its wording. An omitted notice blocks export.
- Stored images are reused, but the PPTX is always reassembled as a whole. Builds report source changes; they do not implement partial ZIP regeneration or automatic pixel-quality judgments. Stable-ID previews provide before/after images for human inspection. Historical builds preserve source snapshots and earlier output decks, not a standalone hermetic copy of every dependency.
- Protection baselines begin with the first successful build. YAML files remain directly editable; enforcement happens on revision/translation/image attachment and on subsequent builds. A determined manual editor can bypass local state; these are workflow safeguards, not a security boundary. Concurrent operations against the same project are not supported; finish one build/revision before starting another.
- Rendering requires optional local software. LibreOffice and Windows PowerPoint use separate adapters; automated tests validate PPTX structure without requiring those applications. CI is configured for Linux, Windows and macOS on Node 22.13 and 24; the Linux Node 22.13 job renders a public typography matrix and uploads only PNG previews and a manifest for seven days. Local PowerPoint output has been visually inspected on selected full-size slides; the remaining matrix images and current LibreOffice output need human review. Generated files contain native title semantics, descriptive object names, localized image/chart descriptions and explicit decorative flags. PowerPoint's Accessibility Checker, Reading Order Pane and a screen reader have not been inspected; follow [the manual review checklist](accessibility-review.md) before delivery.
- PPTimistic distributes the reusable toolkit and fictional bilingual demo only. Private presentation sources, presentation-specific reference images and generated project outputs are excluded.

Next priority: review the current Linux LibreOffice matrix against PowerPoint at full size, record PowerPoint Accessibility Checker and Reading Order Pane results, and improve font diagnostics only where rendered examples show false positives or missed overflow. Any future image or translation adapter needs explicit approval, a spending limit and local fixture tests.

PptxGenJS usage follows its official [chart API](https://gitbrent.github.io/PptxGenJS/docs/api-charts/) and [saving API](https://gitbrent.github.io/PptxGenJS/docs/usage-saving/). The lockfile and an `image-size` override retain patched dependencies; run `npm audit` when updating them.
